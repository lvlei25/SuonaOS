# 蓝牙耳机多点连接（multipoint）与音频占用

> 适用：EDIFIER FitC（本机实测），其他支持 multipoint 的耳机同理。
> 工具：`scripts/20-bt-release.sh`

## 1. 现象

耳机同时连着电脑和手机：

- 电脑上正常出声
- **手机开始播放时，声音出不来**，不会自动切到手机
- 手机上暂停后，电脑这边也正常

## 2. 根因：A2DP 链路没被释放

蓝牙多点切换的规则是：

> 另一台设备要播放时，需要**当前设备的 A2DP 链路空闲**才能接管。

所谓「空闲」就是耳机看到 A 侧发送了 AVDTP SUSPEND。而 Linux 侧只要**还有任何音频流挂在蓝牙 sink 上**，PipeWire 就会把它标成 `RUNNING`，耳机于是认为电脑仍在用，拒绝交棒。

关键点：**「有流」不等于「有声音」**。实测抓到的证据：

```
Sink Input #522
  Sink: bluez_output.6C:16:29:72:22:1C
  Corked: no                    ← 未暂停
  Buffer Latency: 0 usec        ← 但没有缓冲数据
  application.name = "Chromium"
```

```
ID   RATE   NAME
89     0    bluez_playback_internal.6C:16:29:72:22:1C   ← RATE=0，根本没传音频
```

**RATE = 0 却仍是 RUNNING**，耳机无法分辨，于是不切。

## 3. 诊断命令

```bash
# 1) 蓝牙 sink 是 RUNNING 还是 IDLE
pactl list short sinks | grep bluez

# 2) 谁挂在蓝牙 sink 上
pactl list sink-inputs | grep -E 'Sink Input|Sink:|application.name|Corked'

# 3) 是否真的在传数据（RATE=0 说明只是占位）
pw-top -b -n 1 | grep bluez
```

判断：

| 现象 | 含义 |
|---|---|
| sink `RUNNING` + 有流 + `RATE=0` | 被占位，需要释放 |
| sink `RUNNING` + `RATE>0` | 真的在播放，属正常 |
| sink `IDLE` / `SUSPENDED` | 已空闲，耳机可被接管 |

## 4. 工具用法

```bash
# 查看谁占着耳机
./scripts/20-bt-release.sh

# 一键把流移到内置扬声器，耳机随即 IDLE
./scripts/20-bt-release.sh --release

# 前台监控：连续 60 秒无音频数据就自动释放
./scripts/20-bt-release.sh --watch

# 清除 --release 留下的设备记忆（见 4.1）
./scripts/20-bt-release.sh --reset
```

实测输出：

```
蓝牙输出: #661 (bluez_output.6C:16:29:72:22:1C)
内置输出: #61
以下流正占用耳机（会阻止 multipoint 切换）：
  #696   paplay             /tmp/bt-test.oga

$ ./scripts/20-bt-release.sh --release
已移走 #696（paplay）→ 内置输出
共释放 1 个流
耳机当前状态: IDLE          ← 关键：链路已释放
```

### 4.1 副作用：`--release` 会被记成「用户选择」

把流从耳机搬到扬声器时，PipeWire 的 `module-stream-restore` 会把它当成
**你为这个应用手动指定了设备**，并永久记住：

```
$ grep Chromium ~/.local/state/wireplumber/stream-properties
Output/Audio:application.name:Chromium={"...","target":"alsa_output...Speaker__sink"}
```

后果：该应用**之后每次播放都走扬声器**，即使默认设备是耳机。
典型表现就是「浏览器视频的声音出不来」。

清除：

```bash
./scripts/20-bt-release.sh --reset
```

它会删掉指向内置输出的记录并重启 WirePlumber（音频中断约 2 秒）。
只删这类记录，不影响音量与静音状态。

## 5. 治本：找到那个应用

工具只是把流挪开，真正占位的应用还在。常见来源：

| 应用 | 原因 |
|---|---|
| **Chromium / Chrome** | 暂停但未关闭的媒体会话、后台标签的音频元素 |
| 网易云音乐 | 停止播放后流未完全释放 |
| 浏览器 WebRTC | 通话结束后残留 |

Chromium 的查法：

```
chrome://media-internals/
```

看 `Active Players` 列表，或看标签栏上的小喇叭图标。

## 6. 为什么不做常驻服务

实测过开销，两种写法都能用，但**收益不匹配**：

| 方案 | 常驻内存 | CPU | 每日唤醒 |
|---|---|---|---|
| 轮询 10s | 0 | 142 秒 ≈ 0.165% 单核 | 8640 次 |
| 事件驱动 | 5.4 MB | ≈0 | 约 50 次 |

真正成本不是 CPU，而是**唤醒次数**——每 10 秒醒一次会让 CPU 少进深睡，笔记本续航约多耗 0.3~0.5%。

而这个问题的触发频率取决于浏览器行为，可能几天不发生。所以做成**手动命令**更合适；需要自动化时再跑 `--watch`。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示「未找到蓝牙输出设备」 | 耳机未连接 | `bluetoothctl connect 6C:16:29:72:22:1C` |
| `--release` 后没声音了 | 流被移到内置扬声器 | 正常，把流移回或重连耳机 |
| 移完立刻又被占 | 应用重新开了流 | 去关掉那个应用/标签 |
| 耳机本来就在播歌 | `RATE>0`，属正常占用 | 不需要释放 |

## 8. 回滚

脚本不修改任何系统配置，只调用 `pactl move-sink-input`（运行时动作），重启音频服务即恢复默认路由：

```bash
systemctl --user restart wireplumber
```

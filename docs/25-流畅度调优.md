# 25 · 流畅度调优实验记录

> 脚本：`scripts/21-shell-bench.sh`
> 基线定义：`docs/20-流畅度基准.md`　需求：`REQ-33`

## 1. 实验方法与数据

单次静置采样，同一会话、同一机器（T14 Gen 5 / 740M / 3072×1920）：

| # | 配置 | 时长 | shell CPU | shell RSS | GPU 均值 | 频率均值 |
|---|---|---|---|---|---|---|
| A | 基线（模糊 + Suona-Round） | 11s | 11.82% | 360364 KB | 69.2% | 3419 MHz |
| A' | 基线（复测） | 8s | 8.62% | 360469 KB | 68.1% | 3239 MHz |
| B | 关闭 blur-my-shell | 16s | 10.69% | 371970 KB | 67.1% | 3264 MHz |
| C | 关闭 Suona-Round | 12s | 14.58% | 383256 KB | 69.2% | 3189 MHz |
| D | **人工场景**（概览/工作区/快捷设置/滚动） | 63s | 12.51% | 340520 KB | **14.3%** | 2529 MHz |
| E | **人工场景**（同上，第二次） | 212s | 13.33% | 349669 KB | **17.0%** | 2709 MHz |

`--compare` 输出（A → B）：CPU −9.6%、RSS +3.2%、GPU −3.0%、频率 −4.5%，全部落在噪声带内。

## 2. 结论（只写数据支持的）

### 2.1 模糊不是静置负载的主因

关闭 `blur-my-shell` 后 CPU 仅 −9.6%、GPU 仅 −3.0%，均未超过 10% 判据。
`enabled-extensions` 已确认移除该扩展，因此不是「没关掉」。

**这条是负结果，但很有价值**：它排除了「先关模糊保流畅」这种惯性判断。

### 2.2 静置 GPU 68% 是固定底噪，不是桌面开销

三次完全不同配置下 GPU 均值分别是 69.2 / 68.1 / 67.1 / 69.2 —— 几乎不动。
如果是模糊或主题造成的，关掉后应明显下降。因此更可能是
`amdgpu` 的 `gpu_busy_percent` 把**显示引擎/扫描输出**计入，属于该指标的固有底噪。

结论：**本机的 `gpu_busy_avg` 只能做趋势参考，不能当「桌面负载」绝对值使用。**
这一点必须写进文档，否则后续会有人拿 68% 去证明「桌面很卡」。

**人工场景给出了反证**：连续开关概览、切工作区、滚动列表时，GPU 只有 14–17%，
比静置的 68% 低 4 倍。也就是说这个读数不是「GPU 有多忙」，更像是某种静置态的
固定开销（壁纸 XML 过渡 / 静态模糊重绘 / APU 显示引擎计数的组合）。
**处置：把 GPU 从判据里剔除，只在排查「某项改动是否让 GPU 更忙」时看相对变化。**

### 2.3 短窗口静置采样不足以支撑 10% 判据

四组数据的 CPU 从 8.62% 到 14.58%，离散度接近 70%，远超 10% 判据。
原因：11–16 秒窗口里，扩展重载、终端命令、壁纸/服务定时器都会进入样本。

因此修正采样规则（覆盖 `docs/20` 的默认值）：

| 场景 | 最短时长 | 重复 | 取值 |
|---|---|---|---|
| `--idle` | 60s | 2 次 | 取较低值（排除偶发噪声） |
| `--manual` | 60s | 2 次 | 取较低值 |
| 结论门槛 | — | — | 差异 < 10% 一律写「无差异」 |

> 这不是放宽标准，而是承认 20 秒样本的统计功效不足；**宁可不下结论，也不编结论**。

### 2.4 关于缩放（未实测，只给推理，不得当成结论）

有说法「把 200% 改成 150% 会更流畅」。本机未做 A/B，理由与判断如下：

- 3072×1920 在 200% 下逻辑分辨率 1536×960，渲染的物理像素仍是整屏；
- 150% 下逻辑分辨率 2048×1280，**布局元素更多**（更多控件、更多合成图元），
  物理像素并没减少；
- 因此「降缩放 = 更流畅」不成立，甚至可能相反。整数缩放在文本与图标上也不必重采样。

**处置：不改缩放。** 若将来要验证，必须用 `--manual` 场景 + 60s × 2 次，并记录
`monitor_scale`（`metrics.tsv` 已包含该字段）。

## 3. 逐项实验清单

| 嫌疑项 | 状态 | 处置 |
|---|---|---|
| `blur-my-shell`（brightness 0.6 / sigma 30） | 已测（静置） | 无 >10% 差异，保留 |
| `Suona-Round` 叠加 CSS | 已测（静置） | 无有效结论（噪声内），保留 |
| `kimpanel` | 未测 | 与输入法强耦合（ADR-05），不做实验性关闭 |
| 壁纸 XML 过渡（14 张 4K） | 未测 | 属瞬时开销，静置测不出；如要测需录屏/`--manual` |
| `ding` 桌面图标 | 未测 | 低风险，暂不动 |
| 搜索 provider（web/snapd） | 未测 | 只在概览搜索时触发，静置无开销 |
| 200% → 150% 缩放 | 未实测 | 按 §2.4 不改 |

## 4. 给下一次实验的操作单

```bash
# 1) 关掉所有干扰（不要同时跑 apt / 备份 / 壁纸脚本）
# 2) 改前，60s × 2 次
./scripts/21-shell-bench.sh --duration 60
./scripts/21-shell-bench.sh --duration 60

# 3) 只改一项（示例：模糊 sigma 30 → 15）
export GSETTINGS_SCHEMA_DIR="$HOME/.local/share/gnome-shell/extensions/blur-my-shell@aunetx/schemas"
gsettings set org.gnome.shell.extensions.blur-my-shell.panel sigma 15

# 4) 改后，同样 60s × 2 次
./scripts/21-shell-bench.sh --duration 60
./scripts/21-shell-bench.sh --duration 60

# 5) 对比（取较低值那次的目录作为基线）
./scripts/21-shell-bench.sh --compare logs/shell-bench-<改前RUN_ID>
```

判读：

- CPU 与 RSS 同时下降 >10% → 真实收益，保留并记录
- 只有一项动、另一项反向动 → 噪声，回退
- GPU 变化 <5% → 忽略（该指标底噪大）

## 5. 已确认不做的「优化」

| 做法 | 为什么不做 |
|---|---|
| 关掉全部动画 | 观感损失大，且静置测不出收益；真要关用 `enable-animations false`，属于用户偏好不是优化 |
| 卸载 blur-my-shell | 数据不支持「它拖慢系统」，删了只是丢功能 |
| 把缩放降到 150% | 见 §2.4，逻辑上不成立 |
| 禁用 `kimpanel` 换性能 | 会破坏输入法候选框（ADR-05），代价远大于收益 |
| 用 `performance` governor 常驻 | 发热与续航代价高，且掩盖真实瓶颈 |

## 6. 遗留

- ~~`--manual` 场景的前后对比尚未做~~ → **2026-11-15 已完成**：63s / 212s 两次，
  CPU 12.5–13.3%、RSS 340–350 MB、GPU 14–17%。这是后续任何「流畅度优化」的对照基线。
- 人工场景目前只有**同一配置的两次重复**，没有「改前/改后」对照；下次调优时用
  `--compare logs/shell-bench-20261115-140339` 直接比。
- `frame_drop_hint_10min` 六次均为 0，说明 journal 里没有掉帧告警；该方法在本机**没有区分度**，
  只能作为「有没有明显异常」的兜底，不能当指标。
- 人工场景的 CPU 比静置高约 1.5 个百分点（11 → 12.5–13.3），符合「交互有成本」的预期；
  数值不大，说明桌面本身没有明显浪费。

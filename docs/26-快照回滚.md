# 26 · 快照回滚

> 脚本：`scripts/26-snapshot.sh`
> 需求：`REQ-38`　决策：`ADR-34`
> 定位：补上「脚本回滚」管不到的那一层——整机状态。

## 1. 为什么还需要一层快照

`rollback.sh` 只能还原**它备份过的文件**：

| 场景 | `rollback.sh` | Timeshift |
|---|---|---|
| 改错一个 sysctl / gsettings | ✅ 精确 | ✅ 但太重 |
| `apt install` 装坏驱动 | ❌ 不管 | ✅ |
| 误删 `/usr` 下文件 | ❌ 没备份过 | ✅ |
| 内核升级后进不了桌面 | ⚠️ 需手工 | ✅ |
| 恢复到指定时间点 | ❌ 只按批次 | ✅ |

两者**分工不重叠**（ADR-34）：

```
改动来源              回滚工具
脚本改的配置  →  ./scripts/rollback.sh --restore <RUN_ID>
手工/系统改的  →  sudo timeshift --restore
```

## 2. 方案取舍：Timeshift(rsync) 而不是 Btrfs

| 方案 | 优点 | 致命问题 |
|---|---|---|
| **Timeshift + rsync** | 不动分区表，ext4 直接用；增量硬链接省空间 | 同盘快照防不了盘损 |
| Btrfs + snapper | 快照瞬时、可回滚到任意点 | 需要 `btrfs-convert` 在线转换；本机 ext4 + Windows 双系统，失败代价是两台系统一起没 |
| LVM 快照 | 块级、可靠 | 需重装或改分区表，违反项目安全边界 |

结论：**本机用 Timeshift(rsync)**；Btrfs + snapper 留给 UM870 出厂镜像（SREQ-09 已有规划）。
这条不是技术偏好，是**风险预算**：在唯一的开发机上做在线文件系统转换，收益不抵风险。

## 3. 安装与初始化

```bash
./scripts/26-snapshot.sh --install     # 装包 + 检查配置
./scripts/26-snapshot.sh --setup       # 首次必须走一次向导
```

向导里只改三处，其余默认：

| 项 | 选择 | 原因 |
|---|---|---|
| 快照类型 | **RSYNC** | Btrfs 模式需要 Btrfs 根分区 |
| 目标位置 | 本机根分区 | 同盘快照只防误操作；有外置盘再接外置 |
| 排除 | **留空**（不排除 `/home`） | 排除项会让 timeshift 崩溃，见 §3.1；代价是首份快照约 42 GB |

### 3.1 实测：`exclude` 会让 timeshift 直接崩溃

第一次按「排除 /home」配置后，`timeshift --create` 立刻退出：

```
Estimating system size...
** CRITICAL **: string_strip: assertion 'self != NULL' failed
```

换 `LANG=C`、清空 `snapshots` 都无效；把 `exclude` 改成 `[]` 后**同一秒内就开始 rsync**，
161 秒后成功。结论：问题在 exclude 列表，不在 locale、不在设备。

代价：首份快照包含了 `/home`，实测 **42 GB**（根分区 283G，用后剩 101G）。
处置：`26-snapshot.sh --auto-config` 已改为写空 exclude，并打印这条警告（ISSUE-38）。
若要省空间，正确做法是「快照放外置盘」或「业务数据单独备份」，不是硬加 exclude。

初始化完成后建首个基线：

```bash
./scripts/26-snapshot.sh --snapshot "基线"
```

## 4. 日常使用

```bash
./scripts/26-snapshot.sh --status            # 数量 / 占用 / 最近一次 / 是否开启每日
./scripts/26-snapshot.sh --snapshot "改驱动前"  # 高危操作前手动打点
./scripts/26-snapshot.sh --schedule          # 开每日快照（保留 5 份）
./scripts/26-snapshot.sh --prune 5           # 只保留最新 5 份
./scripts/26-snapshot.sh --prune 5 --dry-run # 先看会删哪几份
./scripts/26-snapshot.sh --space-check       # 空间水位（<20G 或 >85% 告警）
./scripts/26-snapshot.sh --restore-help      # 恢复步骤（不自动执行）
```

### 4.1 apt 大改前自动打点

没有做 `DPkg::Pre-Invoke` 钩子——那会让**每次** apt 调用都尝试建快照，慢且容易卡住升级。
改成显式一步，代价是多打一条命令：

```bash
./scripts/26-snapshot.sh --before-upgrade && sudo apt update && sudo apt upgrade
```

规则：30 分钟内已有快照就跳过（避免反复打点）；没有且空间不足则**拒绝**，先清理再升级。
嫌麻烦可以加个别名：

```bash
alias upgrade='~/CodeBuddy/work/linux-tune_SuonaOS/scripts/26-snapshot.sh --before-upgrade && sudo apt upgrade'
```

### 4.2 自动化怎么保证真的会跑

Timeshift 自己的调度不是 systemd timer，而是 `/etc/cron.d/timeshift-hourly`：
cron 每小时检查一次「今天有没有快照」，没有就建。所以验收要看三处：

| 检查 | 命令 | 期望 |
|---|---|---|
| 开关 | `--status` 的「每日快照」 | `true / 保留 5 份` |
| 定时文件 | `ls /etc/cron.d/timeshift-hourly` | 存在 |
| cron 服务 | `systemctl is-active cron` | `active` |

`--schedule` 会把 `schedule_daily=true`、`count_daily=5` 写进配置（备份原文件），
并检查上面两项；`99-verify` 另有「每日快照已启用」「最近快照在 48 小时内」两条断言。

建议打点时机：

- 装/换显卡驱动、内核、桌面大版本之前
- 大批量 `apt install` 之前
- 实验性调优（`docs/25`）之前

## 5. 空间与保留

| 项 | 建议 |
|---|---|
| 保留策略 | 每日 5 份（`--schedule` 写入），手动点按需 |
| 空间占用 | 首份 42 GB（含 /home）；**第二份实测 22 秒、占用仍 42 GB**（增量硬链接复用） |
| 阈值 | `--space-check`：剩余 <20 GB 或已用 ≥85% 告警；`--snapshot` 空间不足时默认拒绝，`--force` 可强写 |
| 清理 | `--prune N`（旧→新排序，保留最新 N）；先 `--dry-run` 看清单 |
| 检查 | `--status` / `sudo du -sh /timeshift` |

**42 GB 怎么对待**：根分区 283G，首份后剩约 100G，5 份日增量很小，可长期维持。
真要省空间只有两条正路——快照放外置盘，或业务数据单独备份；
不要在 `exclude` 里塞 `/home/**`（会让 timeshift 崩溃，ISSUE-38）。

## 6. 恢复（不放进脚本的原因）

Timeshift 恢复会替换系统文件，且常在「进不了桌面」时使用，自动化收益低、风险高。
脚本只提供 `--restore-help`，把步骤固定下来：

1. **能进桌面**：`sudo timeshift --restore`
2. **进不了桌面**：GRUB → recovery mode → root shell
   ```bash
   mount -o remount,rw /
   timeshift --restore
   ```
3. **完全起不来**：Live USB → 装 timeshift → 指定根分区 → 选快照
4. **只救单个文件**：直接去 `/timeshift/snapshots/<时间>/localhost/` 取

## 7. 已知局限（必须写清楚）

| 局限 | 后果 | 应对 |
|---|---|---|
| 同盘快照 | 盘坏 = 快照一起没 | 重要数据另外异地备份 |
| 不覆盖 `/home` 业务数据 | 误删文档救不回 | 代码进 Git，文档进版本库 |
| rsync 需要时间 | 大改后建快照可能几分钟 | 打点放在改动**之前** |
| 不理解 `changes.tsv` | 无法按「某个脚本批次」回滚 | 那种场景用 `rollback.sh` |

## 8. 与 8 步交付清单的关系

第 8 步「回滚与安全」当前判定依据是 `rollback.sh --list` + `rescue.sh --dry-run`。
接入 Timeshift 后，该项应补充断言：**至少 1 个快照存在**。
在此之前，`step-verify.sh` 不会把「装了但没建快照」判为通过。

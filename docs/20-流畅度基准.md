# 20 · 流畅度基准

> 脚本：`scripts/21-shell-bench.sh`
> 需求：`REQ-33`　决策：`ADR-37`
> 定位：**本项目唯一允许产出「顺不顺」结论的证据来源**。

## 1. 为什么单独建基准

`99-verify.sh` 回答的是「配置对不对」，`preboot-check.sh` 回答的是「能不能开机」，
`bench.sh` 回答的是「CPU/磁盘快不快」。三者都回答不了**桌面交互跟不跟手**。

过去所有外观改动只有「改了」，没有「测了」，于是出现两类误判：

| 误判 | 真实原因 | 出处 |
|---|---|---|
| 「换主题后慢了 20 倍」 | EC/SMU 把 CPU 锁在 544MHz | ISSUE-01 |
| 「加了圆角后掉帧」 | 从未测过，纯主观 | — |

所以先建基准，再谈优化。**没有基线的调优一律不接受。**

## 2. 采样项

| 指标 | 来源 | 说明 |
|---|---|---|
| `shell_cpu_pct` | `/proc/<gnome-shell>/stat` 时间片差值 | 桌面进程单核百分比，最直接的「重不重」 |
| `shell_rss_kb` | `/proc/<pid>/status` 的 `VmRSS` | 内存泄漏与主题/CSS 体积的副作用 |
| `gpu_busy_avg/max` | `/sys/class/drm/card*/device/gpu_busy_percent` | amdgpu 占用；无该节点时为 `NA`（不编造） |
| `cpu_freq_avg/min/max` | `cpufreq/scaling_cur_freq` | **有效性判据**，低于上限 50% 直接判无效 |
| `load1_avg` | `/proc/loadavg` | 背景噪声，用于排除「正好在跑 apt」 |
| `frame_drop_hint_10min` | `journalctl --user` 关键词计数 | 只是线索，不是帧率；探不到就记 0 并在文档说明 |

> 诚实边界：GNOME 50 Wayland 下没有对外暴露的逐帧统计接口，
> 本脚本用**代理指标**（CPU/GPU/频率/负载）+ journal 线索衡量流畅度。
> 不做「FPS 60」这种无法复现的宣称。

## 3. 场景

| 场景 | 命令 | 可重复性 | 用途 |
|---|---|---|---|
| 静置 | `--idle`（默认 20s） | 完全可重复，无需交互 | 基线、回归、CI 式巡检 |
| 人工 | `--manual` | 需人按固定动作操作 | 概览/工作区/快捷设置/滚动的真实负载 |
| 对比 | `--compare <dir>` | — | 改动前后量化劣化 |

`--manual` 的固定动作（终端会打印，顺序不要变）：

1. 连续开关「概览」10 次（Super 开、Esc 关）
2. 工作区 2→3→4→1 往返 5 次
3. 展开/收起快捷设置 5 次
4. 在「文件」里滚动长列表 10 秒
5. 打开/关闭一个窗口 5 次

同一场景的前后对比才有意义；`--idle` 基线不能拿来跟 `--manual` 比。

## 4. 阈值规则

| 规则 | 判据 | 动作 |
|---|---|---|
| 测量有效性 | 平均频率 ≥ 上限 50% | 不满足则退出码 2，**先断电复位再测** |
| 回归 | 任一核心指标相对基线劣化 > 10% | 视为可疑，逐项回退实验 |
| 噪声 | 变化在 ±10% 以内 | 视为无差异，不写「优化成功」 |
| 重复性 | 同一天连测两次差异 > 10% | 说明机器状态不稳，当天数据作废 |

**10% 是噪声带，不是目标值。** 不为了让某次改动「看起来有效」而放宽。

> 实测修正（见 `docs/25` §2.3）：20 秒静置样本离散度可达 70%，不足以支撑 10% 判据。
> **现行规则：`--idle` / `--manual` 单次不少于 60 秒，重复 2 次取较低值。**

## 5. 基线

在本机（T14 Gen 5 / Ryzen 5 PRO 8540U / Radeon 740M / 3072×1920）执行：

```bash
./scripts/21-shell-bench.sh                 # 静置
./scripts/21-shell-bench.sh --manual        # 人工场景
```

结果落在 `logs/shell-bench-<RUN_ID>/`：

```
samples.tsv    每秒一行原始采样（可自行画图）
metrics.tsv    汇总指标（键值对，--compare 读这个）
```

实测基线（2026-11-15 13:10–13:11，连续两次 8s/10s 静置）：

| 指标 | 第一次 | 第二次 | 说明 |
|---|---|---|---|
| `shell_cpu_pct` | 8.62% | 11.82% | 第二次测量时同一终端在跑命令，取 8.6–11.8% 为噪声区间 |
| `shell_rss_kb` | 360469 | 360364 | 360 MB 量级，两次几乎一致 |
| `gpu_busy_avg` | 68.1% | 69.2% | **静置就接近 70%，异常偏高**，列入 `docs/25` 首要嫌疑项 |
| `cpu_freq_avg_mhz` | 3239 | 3419 | 上限 4979，占 65–69%，测量有效 |
| `load1_avg` | 0.84 | 1.62 | 第二次含测量自身开销，属噪声 |
| `frame_drop_hint_10min` | 0 | 0 | 该项为线索而非指标 |
| `monitor_scale` | unknown | unknown | 本机无 `~/.config/monitors.xml`，缩放待补测 |
| 人工场景（后续补测） | CPU 12.51% / 63s | CPU 13.33% / 212s | GPU 反而降到 14–17%，见 `docs/25` §2.2 |

两条结论：

1. **静置 GPU 68–69% 不正常**。要么 `gpu_busy_percent` 把扫描输出算进去了，要么桌面确实有常驻 GPU 开销（`blur-my-shell` 是首要嫌疑）。在查清前，任何「GPU 优化」结论都不可信。
2. `shell_cpu_pct` 对同终端并行操作敏感，所以对比必须在**同一台机器、同一场景、无并行任务**下做，且只认 10% 以上的差异。

**未实测就写「流畅」属于违规。**

## 6. 复测流程（每次只改一项）

```bash
# 1) 改前基线
./scripts/21-shell-bench.sh --manual

# 2) 只改一项（例如关掉顶栏模糊）
./scripts/25-...   # 或手工 gsettings，见 docs/25

# 3) 立刻复测
./scripts/21-shell-bench.sh --manual

# 4) 对比（自动挑最新结果）
./scripts/21-shell-bench.sh --compare logs/shell-bench-<改前RUN_ID>
```

判定：

- `shell_cpu_pct` 下降 > 10% 且 `gpu_busy_avg` 同步下降 → 该项确实有开销，可保留改动
- 指标无变化 → 该项与流畅度无关，**不要写进优化结论**
- 指标劣化 → 立即回退，并记录进 `docs/25`

## 7. 与其它脚本的关系

| 脚本 | 回答什么 | 是否可替代 |
|---|---|---|
| `bench.sh` | CPU / sha256 / 磁盘吞吐 | 不能，偏系统吞吐 |
| `21-shell-bench.sh` | 桌面进程负载与交互开销 | — |
| `99-verify.sh` | 配置是否落地 | 不能，偏静态断言 |
| `step-verify.sh` | 交付前 8 步 | 不能，偏交付门禁 |

## 8. 已知局限

- 无逐帧统计，只有代理指标；「偶发一次卡顿」测不出来，只能测持续负载。
- `--manual` 依赖人工动作，两次操作幅度不同会带来噪声；同一人、同一顺序、同一时长可把噪声压到 10% 内。
- 缩放比例不同不可直接对比（渲染像素量不同），`metrics.tsv` 里记录了 `scaling` 供核对。
- 多显示器、外接 4K 场景需单独建基线，不能与内置屏数据混用。

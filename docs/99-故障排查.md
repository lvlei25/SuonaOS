## 2. 按症状排查

### 2.1 开机没有变快

```bash
systemd-analyze
systemd-analyze blame | head -10
systemctl is-enabled NetworkManager-wait-online.service   # 应为 disabled
grep '^GRUB_TIMEOUT' /etc/default/grub                    # 本机为 5（双系统，ADR-03）
```

firmware + loader 那 16 秒是 UEFI POST 与 GRUB 的固有开销，
`Fast Boot` 可在 BIOS 里开（ThinkPad：Startup → Fast Boot = Enabled）。
本机为 Windows 双系统，`GRUB_TIMEOUT` **故意保留 5s**（ADR-03），
因此总开机时间只比基线快约 0.8s，但 userspace 从 11.1s 降到 6.9s；
实测对照见 `00-基线快照.md` 第 9 节。

### 2.2 zram 没起来

```bash
swapon --show
lsmod | grep zram
systemctl status systemd-zram-setup@zram0.service
cat /etc/systemd/zram-generator.conf
```

常见原因：`zram-size` 表达式写错（必须是 `min(ram / 2, 8192)` 这种 generator 能解析的格式），
或内核模块未加载（`sudo modprobe zram`）。

### 2.3 crashkernel 没生效

```bash
cat /proc/cmdline                # 应只有 crashkernel=0，不能有两个
sudo grep -m1 -o 'quiet splash.*' /boot/grub/grub.cfg
grep -r 'crashkernel' /etc/default/grub /etc/default/grub.d/
```

如果出现两个 crashkernel，是 `/etc/default/grub.d/kdump-tools.cfg` 在追加，见 `03-性能优化.md` 第 5 节。

### 2.4 主题只变了一半

> **当前状态**：桌面主题、图标、Dock、字体均已按 ADR-07 回退为系统默认
> （`Yaru-prussiangreen-dark` / 系统 Dock / `Adwaita Sans`）。
> 下表仅适用于你主动重跑 `06-theme-whitesur.sh` 恢复 WhiteSur 之后的排查。

| 现象 | 原因 | 解决 |
|---|---|---|
| 顶栏没变 | user-theme 扩展未启用 | `gsettings get org.gnome.shell enabled-extensions`，注销重登 |
| 图标没变 | 用了 `WhiteSur-Dark` 而非 `WhiteSur-dark` | `ls ~/.icons` 核对大小写 |
| 设置/软件（libadwaita）没变 | 缺 `~/.config/gtk-4.0/gtk.css` | 重跑 `06-theme-whitesur.sh`（带 `-l` 参数） |
| Snap 应用没变 | snap 沙箱读不到 `~/.themes` | 属正常限制，用 deb 版应用 |
| 文件名发白/发灰 | 主题与 color-scheme 冲突 | `gsettings set org.gnome.desktop.interface color-scheme prefer-dark` |

### 2.5 输入法打不出中文

```bash
echo $GTK_IM_MODULE $QT_IM_MODULE $XMODIFIERS    # 必须都是 fcitx
systemctl --user status fcitx5.service          # 自启由 systemd 托管（ADR-04）
fcitx5-diagnose | head -50
pgrep -x fcitx5
```

变量改完必须**注销重登**。若仍是 ibus，检查 `~/.config/environment.d/99-input-method.conf` 是否被别的文件覆盖
（同目录下文件名排序靠后的优先）。登录后没进程看 `systemctl --user status fcitx5.service`，
而不是找 `~/.config/autostart/`（旧方案已废弃）。改候选框主题不生效时，
用 `systemctl --user restart fcitx5.service`，别只 `fcitx5-remote -r`。

### 2.6 脚本报"命令未找到"

```bash
echo $PATH | tr ':' '\n' | grep local
ls ~/.local/bin
```

`~/.local/bin` 不在 PATH 时，`uv` / `bat` / `fd` 都会"缺失"。重新登录或
`source ~/.profile`。项目脚本内部已显式加了这个 PATH，手工执行命令时要自己注意。

### 2.7 脚本中途静默退出

本项目的踩坑记录：

1. **`set -u` + 未定义变量**：基线脚本引用 `$QT_QPA_PLATFORM` 时该变量不存在，
   在 `set -u` 下 shell 直接 `exit`，表现为「脚本打印到一半就没输出了，也没报错」。
   统一改用 `set -o pipefail`，变量写成 `${VAR:-}`。
2. **`cd x && nohup cmd &`**：整个 `cd && cmd` 被放进后台子 shell，
   当前 shell 的 cwd 不变，后续相对路径全部失效。正确写法是 `cd x; nohup cmd &`。
3. **前台命令超时**：耗时操作（GitHub 克隆、apt 装几十个包）放到后台跑，
   用 `tail -f logs/xxx.out` 观察。

### 2.8 蓝牙耳机连接后不从耳机出声

> 本机实例：EDIFIER FitC，已按 ADR-11 修复（ISSUE-14）。

**先确认工具存在**，别用 `2>/dev/null` 吞掉错误。首轮诊断用 `pactl` 时本机没装，
输出全空，差点误判成「没有音频设备」：

```bash
command -v wpctl pw-dump pactl
wpctl status                       # 看 sink / default 标记（*）
pw-dump | grep -i 'default.configured.audio.sink'
```

**根因**：WirePlumber 把一次手工指定持久化成了锁定值。

```
~/.local/state/wireplumber/default-nodes
  default.configured.audio.sink = alsa_output...Speaker__sink
```

于是 A2DP sink 虽然创建成功，默认输出仍指向内置扬声器；更麻烦的是
**已经在播放的流不会自动迁移**，手动切默认设备只对新开的应用有效。

**修复**（两步，缺一不可）：

```bash
# 1. 备份后删除锁定项，让 WirePlumber 回到自动选择
cp ~/.local/state/wireplumber/default-nodes{,.bak}
# 编辑文件，删掉 default.configured.audio.sink 那一行

# 2. 启用自动切换模块，同时处理默认设备与已有流迁移
mkdir -p ~/.config/pipewire/pipewire-pulse.conf.d/
cat > ~/.config/pipewire/pipewire-pulse.conf.d/99-switch-on-connect.conf <<'EOF'
# 由 linux-tune 生成：新输出设备接入时自动设为默认，并迁移已有播放流
pulse.cmd = [
    { cmd = "load-module"
      args = "module-switch-on-connect"
      flags = [ "nofail" ] }
]
EOF
systemctl --user restart pipewire-pulse.service wireplumber.service
```

`pulseaudio-utils`（提供 `pactl`）只是可选诊断工具，**不是修复依赖**。

验收：断开耳机 → 重连 → 不点任何设置，声音应从耳机出来，且正在播放的视频
也跟着切过去。若只切了默认设备、旧流还在扬声器，说明第 2 步没生效。

排查原则：WirePlumber 的「状态文件」优先级高于运行时设置，
**先看 `default-nodes`，再看 `wpctl status`**，不要一上来就重装 PipeWire。

### 2.9 Chromium 点不开 / 闪退 / 无法更新

> 本机实例：2026-11-06，snap 版 Chromium，点击图标无反应，`snap refresh` 也失败。

**先分清是「真崩溃」还是「被锁挡住」**——终端跑一次就能看出来：

```bash
timeout 25 chromium 2>&1 | head -20
```

三种典型输出：

| 输出 | 含义 |
|---|---|
| `另一个 Chromium 进程 (PID) 好像正在使用此个人资料` | **资料锁残留**，见下方修复 |
| `rc=124`（被 timeout 杀掉，无报错） | 其实**能正常启动**，问题在启动器或上次残留 |
| `Failed to start ... AppArmor` / `SSL handshake failed` | 多为噪点，通常不致命 |

**根因一：SingletonLock 残留（最常见）**

Chromium 崩溃、被 `kill -9` 或强制关机后，profile 里会留下三个符号链接：

```bash
ls -l ~/snap/chromium/common/chromium/Singleton*
# SingletonLock -> <主机名>-<PID>    ← 指向的 PID 早已不存在
```

确认 PID 真的不在，再删：

```bash
ps -p <PID> || echo '进程不存在'
cd ~/snap/chromium/common/chromium
unlink SingletonLock; unlink SingletonCookie; unlink SingletonSocket
```

> `unlink` 一次只接受一个文件，不能用 `unlink a b c`。

**根因二：缺 zenity，导致「锁被占用」变成静默闪退**

Chromium 检测到资料被占用时想弹窗让人选择，但系统里没有
`zenity` / `kdialog` / `xmessage`，于是报：

```
Cannot show profile-in-use dialog: no system dialog tool (zenity, kdialog, xmessage) was found.
```

然后**直接退出，没有任何窗口**——看起来就是「点了没反应」。装上即可：

```bash
sudo apt install -y zenity
```

**根因三：snap 更新卡在「应用还在运行」**

`snap refresh` 需要先停掉应用。资料锁或被占用时更新会失败，形成
「打不开 → 更新不了 → 版本还是旧的」循环。解锁后重试：

```bash
snap changes | tail -5          # 看最近一次刷新是 Done 还是 Error
sudo snap refresh chromium
snap list chromium              # 版本 + 修订号应与 /snap/chromium/current 一致
```

**预防**

- 关浏览器用正常关闭，不要 `pkill -9 chromium`；
- 保留 `zenity`（本次已装），至少下次能看到提示而不是闪退；
- 打不开时**先看终端报错**，不要急着重装 snap——重装不解决锁问题。

### 2.10 电池设备 BAT0 消失（重启 upower 后）

**现象**：`/sys/class/power_supply/` 里只剩 `AC`，没有 `BAT0`；
`upower -e` 没有 `battery_BAT0`；GNOME 顶栏电池图标消失。
常见于刚执行过 `systemctl restart upower`（例如改 `/etc/UPower/UPower.conf`）。

**先确认不是硬件**：

```bash
ls -d /sys/bus/acpi/devices/PNP0C0A:00     # ACPI 电池设备还在 → 驱动层问题
dmesg | tail -20 | grep -i thinkpad
```

**修复顺序**：

```bash
# 1) 重新触发 udev 枚举（多数情况无效，但无风险）
sudo udevadm trigger --subsystem-match=power_supply --action=add

# 2) 重载 thinkpad_acpi，让 ACPI 电池重新注册（BAT0 会立即回来）
sudo modprobe -r thinkpad_acpi && sudo modprobe thinkpad_acpi
ls /sys/class/power_supply/BAT0 && upower -e | grep battery
```

重载模块会短暂中断热键/风扇控制，几秒内恢复；充电阈值与健康度不受影响。

**根因**：本机 `thinkpad_acpi` 在充电阈值（75/80）附近会高频重注册电池
（一次启动实测 169 次），与 upower 重启竞争导致 `power_supply` 节点未挂载
（ISSUE-29）。`13-battery-alert.sh` 已封装 `restart_upower_safe()`，
重启后自动检测并自愈，不需要手工处理。

## 3. 回滚

```bash
./scripts/rollback.sh --list
./scripts/rollback.sh --restore 20261103-205748 --dry-run    # 预览
./scripts/rollback.sh --restore 20261103-205748              # 执行
```

参数说明：

| 参数 | 作用 |
|---|---|
| `--restore <RUN_ID>` | 还原该批次所有文件、目录，并重新启用被禁用的服务 |
| `--only <绝对路径>` | 只还原单个文件/目录 |
| `--dry-run` | 只打印将要做什么 |

回滚后需要处理的部分：

```bash
sudo update-grub     # 脚本在检测到 grub 备份时会自动执行
sudo sysctl --system # 自动执行
# 以下需手动/重启
sudo reboot          # GRUB 超时与 crashkernel 恢复
```

## 4. 整体恢复出厂状态

```bash
# 1. 服务与系统配置
./scripts/rollback.sh --restore <第一批 RUN_ID>
./scripts/rollback.sh --restore <第二批 RUN_ID>

# 2. 主题

gsettings reset org.gnome.desktop.interface color-scheme
gsettings reset org.gnome.desktop.wm.preferences button-layout

# 3. 输入法（自启由 systemd 用户服务托管，见 ADR-04）
systemctl --user disable --now fcitx5.service
rm -f ~/.config/systemd/user/fcitx5.service
systemctl --user daemon-reload
rm -f ~/.config/environment.d/99-input-method.conf

# 4. dotfiles
rm -f ~/.zshrc ~/.tmux.conf ~/.vimrc ~/.config/starship.toml

# 5. 重启
sudo reboot
```

## 5. 关机/挂起异常的排查顺序

```bash
journalctl -b -1 -p err --no-pager | tail -40    # 上次启动的错误
journalctl -b -p err --no-pager | tail -40
systemctl list-jobs                              # 卡住的 job
systemd-analyze blame | head -10
```

本项目禁用了 `NetworkManager-wait-online` 与 `apport`，这两项是常见的关机慢元凶；
若关机仍慢，检查 `systemd-suspend.service`（基线里 2.25s）与 USB 设备卸载耗时。
